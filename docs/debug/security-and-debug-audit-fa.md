# ممیزی فنی و امنیتی پورتفولیو — ۱۸ اکتبر ۲۰۲۶

## محدودهٔ ممیزی

ورودی: `KianKhayat-astro-phase9-debugged-source-only(1).zip` از بستهٔ Handoff فاز ۹، همراه با `Kian-Site-Knowledge.pdf`. افزونهٔ `hackingtool-plugin-main.zip` مستقل بررسی شد و داخل سایت نصب/اجرا نشد. ممیزی بر اساس سورس استخراج‌شده و اسناد قبلی انجام شد؛ هیچ آزمون نفوذ عملی روی دامنهٔ زنده انجام نشده است. هر سه دامنهٔ زنده با ابزار مرور وب در این جلسه غیرقابل دسترس بودند.

**اطمینان:** «وجود پیاده‌سازی در سورس» با «تأیید عملکرد در مرورگر»، «درستی تنظیمات سرویس خارجی» و «امنیت عملیاتی روی هاست» یکسان نیست.

## معماری و موجودی تأییدشده

- Astro 7.3.8، خروجی static، TypeScript/CSS، سه خروجی مجزا `dist/en`, `dist/de`, `dist/fa`.
- ۲۰۳ فایل سورس و منابع در ZIP داخلی؛ ۲۱ رکورد JSON: ۷ پروژه، ۸ مدرک، ۴ مقاله، ۲ Featured. ۱۲ مهارت در JSON جداگانه.
- هویت/محتوای فعلی: ۷/۷ پروژه بدون متن مستندات، ۶/۷ فاقد کاور اختصاصی، ۸/۸ مدرک بدون فایل تصویر/PDF، ۴/۴ مقاله بدون کاور؛ ۶/۷ URL مخزن پروژه به GitHub profile اشاره می‌کند.
- محدودسازی محتوای HTML مقاله با `sanitize-html` و `linkedom`، schemaهای Zod، کنترل تصویر/PDF با Sharp، CSP و `_headers` تولیدشده هنگام Build، EmailJS در مرورگر، API بیرونی heatmap.
- `.pages.yml` دارای فرم‌های محتوایی و آپلود رسانه است؛ CMS hosted یک سرویس بیرونی است نه پنل اجراییِ روی این سایت.

## یافته‌ها با اولویت

### P1 — Node engine ناسازگار با dependency

`package.json` حداقل نسخهٔ Node 22.12 داشت، در حالی که نسخه قفل‌شده `undici@8.11.2` به `>=22.19.0` نیاز دارد. روی Node 22.16 هشدار `EBADENGINE` واقعاً مشاهده شد. حداقل Node metadata در بستهٔ دیباگ روی 22.19 قرار گرفت و `.node-version` با مقدار `24` اضافه شد. موفقیت Build با Node 24 در این محیط مجدداً اثبات نشده است.

### P1 — نبود انتشار خودکار در GitHub Actions

`.github/workflows/content-build.yml` فقط صحت‌سنجی، Build و Artifact دارد؛ deploy نمی‌کند. برای Git-based CMS، هر Commit باید سه سایت را منتشر کند. پیشنهاد: اتصال یک مخزن واحد به **سه پروژهٔ Cloudflare Pages**، هر یک با مسیر خروجی متفاوت و تنظیم Node 24. اتصال و مالکیت واقعی DNS مشخص نیست، بنابراین deployment واقعی ساخته نشده است.

### P1 — سیاست حریم خصوصی و ارتباطات بیرونی

`src/pages/privacy.astro` ادعا می‌کند دادهٔ فرم با طرف ثالث به اشتراک گذاشته نمی‌شود، ولی `src/scripts/contact.ts` فرم را به EmailJS ارسال می‌کند. Google Fonts و سرویس heatmap نیز درخواست مرورگر ایجاد می‌کنند. متن پیشنهاد قدیمی در `docs/privacy-proposed-en-de-fa.md` موجود است. متن اصلی بنا به سیاست حفظ محتوای سایت **تغییر نکرد**؛ ویرایش پس از تأیید صاحب سایت انجام شود.

### P1 — ضداسپم و وابستگی به EmailJS

فیلتر مرورگر، طول فیلدها، Honeypot و timeout وجود دارد، اما نمی‌تواند به‌تنهایی abuse سمت سرویس را محدود کند. باید در داشبورد EmailJS: allowlist دامنه‌ها، سقف مصرف، گیرندهٔ ثابت و عدم امکان تغییر مقصد از مرورگر تأیید شود. ارسال واقعی ایمیل تست نشد.

### P2 — فایل‌های PDF صرفاً signature-check می‌شوند

`scripts/media-validation.mjs` برای PDF امضای اول فایل را بررسی می‌کند؛ بررسی malware، ساختار PDF یا محتوای تعبیه‌شده نیست. برای بارگذاری فایل‌های ناشناس از CMS، بازبینی محتوای PDF و محدودیت فرایند بارگذاری لازم است. تصاویر با Sharp و حداکثر ۴۰ مگاپیکسل بررسی می‌شوند، ولی اسکن فایل همچنان لایهٔ جداست.

### P2 — پیچیدگی مدل Featured و محتوای ناقص

۲ رکورد Featured مستقل نمایش را کنترل می‌کنند و boolean قدیمی `featured` موجود در collectionهای دیگر الزاماً نمایش را کنترل نمی‌کند. این رفتار در README توضیح داده شده، اما UX مدیریت آن نیازمند یک قرارداد محتوایی شفاف است. **بدون تأیید صاحب سایت رفتار فعلی تغییر داده نشد.**

### P2 — ابزارهای امنیتی و هدرهای وابسته به هاست

`scripts/harden-output.mjs` برای خروجی ثابت CSP شامل inline script hashes و `_headers` تولید می‌کند. GitHub Pages فایل `_headers` را اعمال نمی‌کند؛ Cloudflare Pages طبق سند رسمی اعمال می‌کند. CSP meta نمی‌تواند جایگزین تمام HTTP headerها از جمله `frame-ancestors` باشد. هدرهای واقعی باید بعد از استقرار با پاسخ HTTP وارسی شوند. `style-src 'unsafe-inline'` باقی است که محافظت CSS را محدود می‌کند؛ حذف آن ممکن است استایل فعلی را بشکند و نیازمند تست مرورگر است.

### P2 — وابستگی سرویس heatmap و فونت

Heatmap به API خارج از سایت وابسته است و کد برای شکست درخواست fallback دارد. فونت‌های Google نیز وابستگی بیرونی ایجاد می‌کنند. صحت fallback، سرعت موبایل، Cumulative Layout Shift و مسائل حریم خصوصی باید در مرورگر تست شوند. اعداد Lighthouse **اندازه‌گیری نشدند**.

### P2 — قابلیت‌های CMS هنوز عملیاتی تأیید نشده‌اند

`/admin/` صفحهٔ راهنما و لینک به Pages CMS است، نه احراز هویت اختصاصی در سایت. ورود OAuth، دسترسی به مخزن، ذخیرهٔ تصویر از موبایل، Commit و انتشار بعد از Save باید توسط مالک تأیید شوند. فایل‌های `draft` در مخزن عمومی حتی اگر در سایت نمایش داده نشوند، عمومی هستند.

## یافته‌های امنیتی و مرز اعتبار

- **XSS:** یک مسیر `innerHTML` برای مقاله در `src/scripts/modals.ts` و چند `set:html` در Astro وجود دارد. `safeArticleHTML` در مرحلهٔ Build برای مقاله‌ها به‌عنوان کنترل اصلی طراحی شده و JSON داخل script عناصر `<` را escape می‌کند. **از روی بررسی ایستا آسیب‌پذیری XSS اثبات نشد**؛ تست‌های موجود باید پس از نصب وابستگی اجرا شوند.
- **Command Injection / SSRF در سایت:** در سورس استاتیک سایت backend کاربرمحور یا runner اجرای shell وجود ندارد. آسیب‌پذیری قابل بهره‌برداری در این زمینه اثبات نشد.
- **Secrets:** الگوهای مشخص GitHub/OpenAI/AWS/Telegram/Pem در فایل‌های متنی پروژه پیدا نشدند؛ شناسه‌های EmailJS در `src/data/email.ts` از نوع public identifier هستند، نه کلید خصوصی. secret history و متغیرهای محیطی host دیده نشدند.
- **تزریق فایل:** اعتبارسنجی فایل، path containment و تشخیص MIME تصویر در سورس دیده شد؛ عملکرد واقعی unit tests به علت npm نصب‌نشده دوباره اجرا نشد.
- **هدرها:** CSP، X-Frame-Options، nosniff، Referrer-Policy، Permissions-Policy و HSTS در generator دیده شدند؛ اثربخشی در پاسخ زنده هنوز تأیید نشده است.

## افزونهٔ امنیتی در ZIP دوم

`hackingtool-plugin-main.zip` یک افزونهٔ ابزارمحور **برای Claude** است، نه نرم‌افزار میزبانی یا وب‌اپلیکیشن. در `tools.json` تعداد ۱۸۳ ابزار فهرست‌شده در ۳۰ دسته وجود دارد؛ فقط ۵۶ مورد با نشانگر `runnable_by_claude` مشخص شده‌اند. شش ماژول Python از نظر syntax سالم بودند. فایل `ht_run.py` امکان اجرای دستورات از طریق shell، imageهای Docker با tagهای بدون pin، `--privileged` و retry خودکار با sudo دارد. **این موارد ریسک اجرای کد با امتیاز بالا و supply chain هستند**؛ افزونه را در سرور production یا روی سورس‌های محرمانه به طور خودکار اجرا نکنید. در این ممیزی هیچ ابزار تهاجمی افزونه اجرا نشده است.

## روند عیب‌یابی قابل تکرار

1. Node.js 24 را نصب و `node --version` را کنترل کنید.
2. در ریشه پروژه `npm run debug:preflight` را اجرا کنید؛ گزارش در `docs/debug/source-preflight.json` نوشته می‌شود.
3. `npm ci`، `npm audit --audit-level=high` و `npm run test:security` را اجرا کنید.
4. `npm run test:editorial`، `npm run check:cms`، `npm run build` و `npm run check:seo` را اجرا کنید.
5. `npx playwright install chromium` و بعد `npm run test:e2e` را اجرا کنید.
6. ترمینال اول: `npm run preview`. ترمینال دوم: `npm run debug:local`. گزارش در `docs/debug/local-smoke.json` ثبت می‌شود.
7. بعد از استقرار، HTTPS/TLS، هدرهای واقعی، Lighthouse موبایل، فرم تماس واقعی، OAuth/CMS و DNS سه دامنه را بررسی کنید.

**تفسیر نتیجه:** عبور همهٔ تست‌ها نیز نبود تمام آسیب‌پذیری‌ها را ثابت نمی‌کند. به‌خصوص npm audit و Playwright به دلیل شکست نصب وابستگی در این جلسه انجام نشدند.
