# کوتاه‌ترین مسیر انتشار پس از تأیید فاز ۹

این فایل راهنماست؛ هیچ حساب یا دامنه‌ای در این فاز تغییر نکرده است.

## ۱. تأیید متن

پیش‌نویس `privacy-proposed-en-de-fa.md` را تأیید یا اصلاح کن و مدت نگهداری پیام‌های تماس را تعیین کن. متن فعلی صفحه عمداً حفظ شده و برای انتشار نهایی باید با رفتار واقعی هماهنگ شود.

## ۲. گیت‌هاب و پنل

- سورس را در ریشهٔ یک شاخهٔ آزمایشی مخزن قرار بده؛ `.pages.yml` و `.github` را هم منتقل کن.
- در `https://app.pagescms.org/` با GitHub وارد شو؛ برنامه را فقط برای همین مخزن نصب و شاخه را انتخاب کن.
- یک مقالهٔ پیش‌نویس بساز، ذخیره کن و سبزشدن `Validate and build content` را در Actions ببین. پیش‌نویس در مخزن عمومی محرمانه نیست.

## ۳. میزبانی و DNS

هر زبان باید در ریشهٔ دامنهٔ خودش سرو شود: انگلیسی `dist/en`، آلمانی `dist/de` و فارسی `dist/fa`. کل پوشهٔ `dist` را به یک دامنه متصل نکن.

فایل `_headers` برای میزبان‌هایی مانند Cloudflare Pages آماده است. GitHub Pages این فایل را اجرا نمی‌کند؛ CSP متا بخشی از حفاظت را نگه می‌دارد، اما هدرهای امنیتی HTTP باید در میزبان یا پراکسی سازگار تنظیم شوند. انتقال میزبان بدون تصمیم صاحب سایت انجام نشده است.

اگر Cloudflare Pages انتخاب شد:

- سه پروژه به همان مخزن و شاخه متصل کن. فرمان ساخت هر سه `npm run build` و Node نسخهٔ ۲۴ باشد؛ پوشهٔ خروجی به‌ترتیب `dist/en`، `dist/de` و `dist/fa` است.
- ابتدا از بخش Custom domains هر پروژه، دامنهٔ متناظر را اضافه کن؛ سپس DNS دقیق پیشنهادی همان داشبورد را تنظیم کن. مقصد CNAME را از خود پروژه بردار، نه یک نام حدسی.
- اتصال دامنهٔ اصلی به Pages نیازمند zone فعال Cloudflare است. پیش از هر تغییر nameserver، رکوردهای ایمیل MX/TXT و سایر رکوردهای فعلی را حفظ کن. برای زیردامنه با DNS خارجی، مسیر CNAME ارائه‌شدهٔ داشبورد را دنبال کن.
- پیش‌نمایش آزمایشی را با کنترل دسترسی میزبان محافظت کن. روی دامنهٔ نهایی، HTTPS، مسیر `/work/`، یک مقاله و ۴۰۴ واقعی را بررسی کن.

اگر GitHub Pages حفظ شد، راهنمای `domain-setup-fa.md` برای خروجی‌های مستقل کاربرد دارد؛ برای دریافت تمام هدرهای این نسخه تنظیم جداگانهٔ میزبان/پراکسی لازم است. گردش کار همراه پروژه فقط خروجی می‌سازد؛ استقرار خودکار برای GitHub Pages هنوز پیکربندی نشده است.

## ۴. EmailJS

- در قالب، گیرنده ثابت، فرستنده پیش‌فرض سرویس، Reply-To برابر `{{email}}` و متن شامل `{{name}}`، `{{subject}}` و `{{message}}` باشد.
- در تنظیمات امنیتی حساب، فقط سه مبدأ `https://kiankhayat.me`، `https://fa.kiankhayat.me` و `https://de.kiankhayat.me` را مجاز کن. برای آزمایش موقت، فقط مبدأ لازم را اضافه و پس از پایان حذف کن.
- یک پیام واقعی از سایت نهایی بفرست و دریافت و پاسخ را بررسی کن. سایت همچنان `cian@kiankhayat.me` را نشان می‌دهد؛ موجودبودن یا فوروارد آن صندوق مستقل از EmailJS است.

## ۵. بررسی نهایی

پس از نصب وابستگی‌ها، این دستور فقط درخواست خواندن به سه سایت واقعی می‌فرستد و ایمیلی ارسال نمی‌کند:

```sh
npm run check:live
```

زبان، canonical، هدرها، sitemap، RSS، عدم نمایه‌سازی ورودی پنل و پاسخ ۴۰۴ بررسی می‌شوند؛ گزارش در `docs/phase9/live-check.json` است. موفقیت این دستور به معنی آزمون ورود CMS یا تحویل ایمیل نیست. برای پیش‌نمایش محلی ابتدا `npm run preview` و در ترمینال دوم `npm run check:live -- --local` را اجرا کن.

در Search Console نقشهٔ `/sitemap.xml` هر سه دامنه را ثبت کن. متادیتای فارسی آماده است؛ زمان نمایه‌سازی و متن نهایی نتایج قابل تضمین نیست.
